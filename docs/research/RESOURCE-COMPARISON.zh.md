# 资源比较报告（2026-10-25）

在本次受控 Chrome 夹具中，省资源档（economy）观察到比标准档（standard）更低的浏览器进程树 CPU 占用，并且实际执行了更少的持续调度、鲸群积分与绘制工作。该结论仅覆盖这台机器、这份构建和模拟场景，不能外推为实际 DSH 的资源收益、运行加速或续航改善。关闭插件（off）的 CPU 仍最低。

计算公式为 `单核等效 CPU % = Σ(进程 CPU 秒数之差) ÷ (CPU 观察窗口毫秒数 / 1000) × 100`。分母采用采集 CPU 前后记录的 `elapsedMs`，包含查询边界开销，不用标称 60 秒替代。整机归一化值再除以 16。单核等效 100% 表示占用一个逻辑处理器的时间量，42.520% 不是占整台电脑的 42.520%。

CPU 范围包括隔离 Chrome 的 browser、renderer、GPU 与 utility 进程，以及夹具和 Chrome DevTools Protocol（CDP）操作带来的开销。它不是插件独占 CPU，也不是 GPU 利用率。45 个样本的前后进程身份及类型集合全部稳定，CPU 时间差均非负，重算值与存储值在浮点精度内一致。没有把独立剖析的 CPU 数值混入这张表，也没有减去历史 off 值计算“净插件收益”。

三个场景中 economy 与 standard 的范围均未重叠，支持“本受控批次观察到较低 CPU”。背景噪声仍存在，例如 standard 静置最大值 51.436% 高于其中位数 42.520%。这些绝对值不提供跨设备比例、通用加速倍数、电量节约或电池续航保证。

standard 的持续调度使用 RAF，economy 使用 timer，活动通道回调数与 `wakeup` 一致，另一通道为零。内部积分从约 3600 次变为约 1800 次，说明减少的是实际推进，不只是少画几帧。静置持续绘制从 1600 次变为 768 次。配置还把游速倍率设为 0.75，因此两档不承诺相同的视觉时间采样或游动速度。

追加文本带来布局刷新。standard 的总绘制中位数 1680 含 239 次 `foreground` 前景刷新，持续动画部分为 1441；economy 分别为 772、239、533。布局测量不是额外的 draw 原因，本批绘制时间线只有 `animation` 和 `foreground`。两档追加场景的插件布局计数均为 480 [480, 480]，因此不能说所有工作都减半，也不能把总绘制数直接用于持续帧预算。

持续动画上限由[资源策略](../../src/resource-policy.js)设为 standard 30 次/秒、economy 15 次/秒。审计逐份核对持续绘制的数量及开始时间间隔，均在各自预算内。追加内容或任务状态触发的刷新走独立路径，不受持续动画 15 次/秒上限阻塞。250 ms 任务提示阈值是另一项检查，不能拿持续帧间隔代替。

初始化阶段观测到的 RAF 间隔中位数为 6.3 ms，45 个单元的中位间隔范围为 6.2–6.3 ms。这只是 headless RAF 回调间隔，不能换算成显示器物理刷新率。公开字段 `physicalRefreshRate` 仍未测。

## 限制因素与源码归属

独立诊断批次完成九单元，并记录浏览器退出成功。其源码哈希与完整采样相同，但诊断包关闭压缩并带源码映射，正式采样包使用压缩。逐一解析九份 CPU profile 的 `samples`、`timeDeltas` 和节点，按实际落在节点上的时间求和。下表只作热点定位，不能用其数值算正式 CPU 收益。

| 函数及当前源码 | 归属 | standard 静置诊断 self time（ms） |
| --- | --- | --- |
| [atmosphereCloudAt](../../src/atmosphere.js#L82) | 云影场采样，绘制与海面遮罩路径 | 504.448 |
| [deformWhaleParticle](../../src/rig.js#L82) | 鲸体、鳍尾与脊柱变形 | 489.426 |
| [resolveDepthGrid](../../src/model.js#L337) | 投影三角形的深度和字格覆盖解析 | 369.793 |
| [transformParticle](../../src/model.js#L263) | 变形后的坐标与法线变换 | 196.524 |
| [attenuation](../../src/model.js#L530) | 视口边缘和阅读中心的透明度衰减 | 174.054 |

这些热点在另外两个 standard 场景及 economy 诊断中也出现。它们属于绘制路径，不能把所有热点都归为低频 `atmosphereUpdate` 或 `motionStep`。off 诊断主要为空闲，追加和滚动的 `dispatch`、`snapshot` 未成为命名 JavaScript 热点的主要成本；这仍不能排除浏览器原生布局、栅格与 CDP 开销。

可核实的限制是主动调度节奏及每次绘制成本。[调度实现](../../src/engine.js#L748)在 economy 一次工作结束后才预约下一个 66.7 ms timer，工作本身和调度延迟会加到间隔上，因此上限 15 次/秒不等于实际达到 15 次/秒。静置总同步 draw 耗时为 standard 11850.1 [11765.9, 14208.8] ms、economy 6120.0 [6056.0, 6333.0] ms，n = 5；同期 `advance` 仅为 351.2 [336.9, 416.3] ms 和 105.3 [98.9, 108.1] ms。减少昂贵绘制的调用次数与观察到的 CPU 下降相符。

这些计时互有嵌套，不能相加为浏览器 CPU，也不能作为 GPU 提交完成时间。诊断页面线程大量时间处于 idle，不能宣称某核已饱和或 GPU 是整机瓶颈。正式静置样本中，renderer 的 CPU 秒数中位数为 15.627 与 7.208，GPU 进程的 CPU 秒数中位数为 9.843 与 4.665，均各 n = 5。后者表示 GPU 进程占用的 CPU 时间，不能推出 GPU 引擎忙碌率。仍未取得 GPU 利用率、GPU 时间线或硬件功耗，不能把剩余开销精确归因给某个硬件限制。
